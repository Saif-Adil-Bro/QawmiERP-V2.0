# রাউন্ড ৭ — যাচাই ও লাইভ চালুর শর্ত

**সিদ্ধান্ত: প্রোডাকশন এখনও যাচাই করা হয়নি।** নিচের ফল বিচ্ছিন্ন PostgreSQL, Auth/Data API এবং অ্যাপের নিজের UI/HTTP পথের। লাইভ ছয়টি ডিসেম্বর বিল, নূরুল ইসলামের বরাদ্দ, মূল গেটের যন্ত্র, পুরোনো ম্যাপিং বা হাজিরায় কোনো পরিবর্তন করা হয়নি। মূল সাত লাইনের ফাইল বা আসল হার্ডওয়্যার পাওয়া যায়নি; সমতুল্য নমুনা ব্যবহার করা হয়েছে। [আগের বায়োমেট্রিক পরিকল্পনা](biometric-followup7-fix-plan.bn.md) আলাদা করে রাখা আছে।

**যাচাইয়ের ফল:** production build ও TypeScript পরীক্ষা সফল; **২৫৪/২৫৪ unit, ১৪৯/১৪৯ e2e**। PostgreSQL-এ finance-এর ১২টি এবং Round 7-এর ৭টি পরীক্ষাগুচ্ছ সফল, আলাদা cluster-এ cold restore-সহ। নিচের UI ফলগুলো Chromium-এ চালানো হয়েছে; এগুলো source-code string বা mocked response-এর দাবি নয়।

### সাত লাইনের পড়া

নমুনায় প্রথমবার: **৪ নতুন আনম্যাপড + ১ ডুপ্লিকেট + ২ বাতিল**, হাজিরা ০। দ্বিতীয় ও তৃতীয়বার প্রতিবার: **০ নতুন + ৫ ডুপ্লিকেট + ২ বাতিল**; তিনটি সম্পন্ন ইমপোর্টের পর পাঞ্চ ৪, হাজিরা ০। `ABC` ও `23/11/2026 08:15` লাইন নম্বরসহ বাতিল; বৈধ অচেনা `999999` অপেক্ষমাণ থাকে। `480001`-এর ২৩ নভেম্বর `07:55` → `01:55Z` → ঢাকায় `07:55`। PIN ম্যাপ করে তার দুটি পাঞ্চ আলাদাভাবে যাচাই ও অনুমোদন করলে এক ব্যক্তি-দিন উপস্থিত, অন্য দুই PIN অমীমাংসিত। একই PIN-এর ২২ তারিখের নতুন JSON push-এ ১টি উপস্থিতি হয়েছে। একই instant iClock ও push-এ আবার পাঠিয়ে মোট ১টি event ও ১টি উপস্থিতিই ছিল। **১৮টি পুরোনো আনম্যাপড log একই ছাত্রের ধরে batch replay করবেন না।**

**ডিভাইস, লোড ও পুনরুদ্ধার:** সংযোগ-পরীক্ষার HTTP অনুরোধ ধরে থাকাকালে সংশ্লিষ্ট বোতামে busy/disabled, পরে সৎ offline ফল। Auto-map-এ প্রথমবার ১টি নতুন, দ্বিতীয়বার ০টি নতুন। ডিভাইস কার্ডে ৪ পাঞ্চ। সরু পর্দায় cancel → আবার delete → confirm → reload: শুধু `TESTSERIAL0001` সরেছে; `Real main gate`-এর সম্পূর্ণ registry row ও সব পাঞ্চ অপরিবর্তিত। তারিখ/ডিভাইস ফিল্টারে একই সময়ের ১০১ পাঞ্চ দুই পৃষ্ঠায় ১০০ + ১; গণনা পড়তে না পারলে ০ নয়, ত্রুটি দেখা গেছে। দুটি সম্পূর্ণ স্থানীয় রানে প্রথম কার্ড যথাক্রমে ০.৯২ সেকেন্ডে (২টি server-action অনুরোধ) ও নতুন fixture build-এ ৭.৫৬ সেকেন্ডে (৪টি অনুরোধ) এসেছে। এটি live SLA নয়; রিপোর্টে বলা ২০–৫৫ সেকেন্ডের সঙ্গে পরিবেশও এক নয়।

পরীক্ষায় শুধু হাজিরা মডিউলের export → private snapshot-এর checksum যাচাই → অনুমোদিত wipe → সেই snapshot দিয়ে HTTP restore চালানো হয়েছে। ১০৬টি event row হুবহু ফেরত এসেছে; অন্য প্রতিষ্ঠানের পাঞ্চ ও ছয়টি ডিসেম্বর বিল অক্ষত। আলাদা cold restore-এ দুর্বল role-এর read grant-ও ফেরত আসেনি। **অপারেটরের রিপোর্টের পুরোনো ২২ log (২৩ তারিখে ১৮, ২৫-এ ৩, ২২-এ ১) fixture-এর পাঞ্চ বা ২২টি হাজিরা নয়।**

## FOLLOWUP6-এর আলাদা হিসাব

## ৩০ নভেম্বরের মধ্যে অপারেটরের করণীয়

1. **আগে ব্যাকআপ ও baseline।** সঠিক tenant শনাক্ত করে লাইভ DB ও প্রয়োজনীয় private storage-এর ব্যাকআপ নিন; বিচ্ছিন্ন কপিতে restore করে খুলুন। ৬ বিলের ID, দুই খাতা, মাস, ফি-খাত, payable/paid/due, এবং মূল গেট, পরীক্ষার যন্ত্র, ২২ নভেম্বরের হাজিরা ও ২৩–২৫ তারিখের লগ গুনে রাখুন। শুধু স্ক্রিনে ৬ লেখা যথেষ্ট নয়। মূল ঘটনাগুলো পুনরায় তৈরি বা `forceUpdate` করবেন না।
2. **SQL আগে, অ্যাপ পরে।** [Finance prerequisite/rollout](finance-integrity-rollout.bn.md) অনুযায়ী base, account model, portal parity ও বিদ্যমান finance/treasury schema যাচাই করুন। Restored staging-এ এই শাখার **আপডেটেড** `supabase_finance_integrity_migration.sql`, প্রযোজ্য `supabase_finance_cashbooks_migration.sql`, তারপর `supabase_round7_migration.sql` পরীক্ষা করুন। আগের migration ব্যর্থ হলে থামুন। নতুন migration কোনো ঐতিহাসিক পাঞ্চ/হাজিরা বা ডিসেম্বর বিল backfill করে না। `biometric_punch_events` ও RPC-গুলোর RLS/grants যাচাই করুন; `anon`/`authenticated`-কে service grant দেবেন না।
3. **একই release-এ writer বদলান।** আগের USB/push writer, চলমান import, cron ও অ্যাডমিন save থামিয়ে অনুমোদিত deployment করুন। পুরোনো tab রিফ্রেশ করুন। নতুন অ্যাপটি সত্যি সঠিক DB-তে চলছে নিশ্চিত করে writer চালু করুন। Schema না থাকলে error দেখাই প্রত্যাশিত; fallback হিসেবে পুরোনো অনিয়ন্ত্রিত insert চালাবেন না।
4. **ট্রিগার থেকে tenant পর্যন্ত যাচাই করুন।** `RAILWAY_APP_URL`-এ সঠিক production HTTPS origin এবং Actions ও হোস্টে একই `CRON_SECRET` আছে কিনা অপারেটর **মান প্রকাশ না করে** যাচাই করবেন। GitHub workflow প্রতি ১৫ মিনিটে `/api/cron/dispatch`; `vercel.json`-এর ১৫ মিনিটের সূচি ব্যবহার করলে হোস্টের plan সেটি সমর্থন করে কিনা দেখুন। দীর্ঘস্থায়ী production Node/Railway-এ in-app tick-ও থাকতে পারে; preview/build-কে production trigger বানাবেন না। ২৫ নভেম্বরের Actions call-step সফল হওয়া tenant-এর job success-এর প্রমাণ নয়; Vercel deployment ব্যর্থতার কারণও এখান থেকে নিশ্চিত নয়।
5. **টার্গেট প্রতিষ্ঠানে readback।** `/dashboard/settings/automation`-এ দুই পৃথক সময়ে persisted heartbeat, trigger source, `monthly_fee_generation`-এর enabled/cron/timezone, শেষ attempt ও next cursor মিলিয়ে নিন। শেষ হওয়া জবের ID, `SUCCESS`/`FAILED`, period, generated/skipped/failed দেখুন। `RUNNING` আটকে গেলে বা heartbeat পুরোনো হলে host log ও write grant যাচাই করুন। মাসিক বিলের interlock ছাড়া reminder/notification-এর অন্ধ retry নয়। Production-এ পরীক্ষার জন্য সব জব একসঙ্গে চালাবেন না।
6. **লাইভ ডিসেম্বর গেট।** DBA-র read-only পর্যালোচনার জন্য [round7-readback.sql](../scripts/sql/round7-readback.sql)। একই SQL session-এ `qawmi.review_tenant`-এ যাচাই করা UUID সেট করুন; রিপোর্ট নিজে কোনো tenant বেছে নেয় না। SQL automation table না থাকলে report থামবে—সেই ক্ষেত্রে `madrasa_settings`-এর সংশ্লিষ্ট fallback ও অনুমোদিত UI পরীক্ষা করুন। একই cut-off-এ baseline ও ফল তুলুন: ছাত্র/ফি-খাত/মাস, ৬ বিল, ৳১১,৬০০ ও full-row fingerprint। SQL/JSON mirror থাকলে সেটি নতুন আয় নয়। নতুন বাস্তব লেনদেন হলে আলাদা করে reconcile করুন; অমিলকে “সফল” বলবেন না। **১ ডিসেম্বর ০৭:০০ BDT-এর প্রকৃত রান শেষে এই যাচাই আবার করতে হবে।**
7. **শুধু পরীক্ষার যন্ত্র।** অনুমোদিত অপারেটর tenant + নির্দিষ্ট device ID + `TEST-BIOMETRIC-DELETE-ME` + `TESTSERIAL0001` চারটিই মিলিয়ে dialog থেকে মুছবেন। reload করে পরীক্ষার যন্ত্র নেই, **আসল মেইন গেট আছে**, পুরোনো পাঞ্চ, manual mapping ও ২২ নভেম্বরের হাজিরা আছে—সব মিলিয়ে নিন। মিল না পেলে থামুন। Fixture-এ deletion মানে লাইভ cleanup নয়।

**থামা/পুনরুদ্ধার:** অর্থ, tenant, auth, অডিট বা হাজিরার যেকোনো অমিলে cron/import/replay ও সংশ্লিষ্ট write বন্ধ রাখুন। ইতিমধ্যে তৈরি receipt, event, job UUID ও snapshot সংরক্ষণ করুন। সম্পূর্ণ পুরোনো JSON ফেরত লেখা, পুরোনো timestamps থেকে গণহারে ছয় ঘণ্টা বিয়োগ বা migration `DROP` করা rollback নয়। DBA ও হিসাবরক্ষক বিচ্ছিন্ন restored copy-তে নতুন লেনদেন মিলিয়ে অনুমোদিত roll-forward/restore ঠিক করবেন।

## পরীক্ষা আবার চালাতে

Deployment env ফাইল বা hosted credential ছাড়া পরিষ্কার test checkout ব্যবহার করুন। DB পরীক্ষাগুলো নিজের cluster সৃষ্টি ও পরিষ্কার করে; production DSN নেয় না।

```sh
npm ci
npm run lint && npm test && npm run test:e2e && npm run build
export QAWMI_PG_BIN="$(pg_config --bindir)"  # non-root, initdb/pg_ctl সহ
npm run test:finance:sql && npm run test:round7:sql
npm ci --prefix tests/sql/session --ignore-scripts
TOOLS="$(mktemp -d)"
npm install --prefix "$TOOLS" --no-save playwright-core@1.65.1 @sparticuz/chromium@158.0.0
QAWMI_BROWSER_TOOLS="$TOOLS" npm run test:round7:browser
```

Chromium চালাতে OS-এর NSS/NSPR libraries প্রয়োজন। Browser fixture disposable provider-এর public key/URL সহ নিজের Next build করে, আসল HTTP route/server action ও browser dialog চালায়। UI এবং DB-তে দুদিক থেকে ফল মেলে; fixture কোনো real device বা production gateway-র বিকল্প নয়।
