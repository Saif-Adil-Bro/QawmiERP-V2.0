# FOLLOWUP7 — বায়োমেট্রিক হাজিরা: কারণ, সংশোধন ও যাচাই পরিকল্পনা

**পরিধি:** `/dashboard/attendance/devices` ও একই পাঞ্চ গ্রহণকারী USB, iClock ও JSON push পথ। FOLLOWUP6, নতুন হার্ডওয়্যার ইন্টিগ্রেশন ও হাজিরার নীতি পরিবর্তন এর বাইরে। এটি পরিকল্পনা; কোনো অ্যাপ ফিক্স, migration বা ডেটা পরিষ্কার করা হয়নি।

**মূল সিদ্ধান্ত:** ডিলিট ও অটো-ম্যাপের বাটনে হ্যান্ডলার আছে; শুধু বাটন নতুন করে জুড়লে সমস্যার সমাধান হবে না। অন্যদিকে পাঞ্চের ভুল সময়, ভুল তারিখকে আজ ধরা এবং একই পাঞ্চ বারবার সংরক্ষণ—তিনটিই বর্তমান কোডে যাচাই করা গেছে। এগুলো ঠিক না করে পুরোনো পাঞ্চ পুনঃপ্রক্রিয়া করলে ভুল দিনের হাজিরা স্থায়ী হতে পারে।

## প্রমাণ ও সীমা

নিচে **UI** = [BiometricDevicesClient.tsx](../app/dashboard/attendance/devices/BiometricDevicesClient.tsx), **Action** = [app/actions/biometric.ts](../app/actions/biometric.ts), **Parser** = [lib/biometric.ts](../lib/biometric.ts)। লাইন নম্বর এই পর্যালোচনার সংস্করণের।

- **স্থানীয় যাচাই:** প্রকৃত parser ও server action চালানো হয়েছে; ঘড়ি রিপোর্টের পরীক্ষার তারিখে স্থির, পরিচয়/roster/storage/attendance লেখার জায়গায় মেমরির নকল সেবা। মূল পরীক্ষার ফাইল নয়, একই বৈশিষ্ট্যের সাতটি নমুনা লাইন। `07:55` থেকে parser দিয়েছে `07:55Z` (ঢাকায় `13:55`); `23/11/2026 08:15` থেকে পেয়েছি `2026-11-25`; `ABC` ও একই পাঞ্চের দুই কপি দুটোই গ্রহণ করেছে।
- ম্যাপিং ছাড়া তিনবার ইমপোর্টে **২১ লগ, ডিভাইস কাউন্টার ০**। পরে `480001` ম্যাপ করায় পুরোনো লগ বদলায়নি; ২২ নভেম্বরের নতুন পাঞ্চে `Present` লেখার অনুরোধ হয়েছে। শেষে ২৩ তারিখে ১৮টি ও ২৫ তারিখে ৩টি আনম্যাপড, ২২ তারিখে ১টি প্রসেসড—রিপোর্টের বণ্টনের সঙ্গে মেলে। নকল স্টোরে write ব্যর্থ করলেও delete `success:true`; roster query ব্যর্থ করলেও auto-map `success:true, totalMapped:0`। এগুলো বর্তমান ত্রুটির প্রমাণ, ফিক্স পাসের ফল নয়।
- **এখনও অনিশ্চিত:** রিপোর্টের ব্রাউজারে ক্লিক ঠিক কোথায় থেমেছে, ২০–৫৫ সেকেন্ডের কতটা সার্ভার/নেটওয়ার্কে, ও ওই প্রতিষ্ঠানের প্রকৃত DB schema। ব্রাউজার ট্রেস, চালু DB বা আসল মেশিন পরীক্ষা করা হয়নি।

## সমস্যা ধরে করণীয়

### ১. ডিভাইস মোছা

UI:695–702 থেকে `handleDeleteDevice` কল হয়। UI:199–211-এ native `confirm()` মিথ্যা ফেরালে কোনো অনুরোধ বা বার্তা ছাড়াই `return`; action-এর promise প্রত্যাখ্যাত হলেও হ্যান্ডলারে `catch` নেই। এমবেডেড ব্রাউজারে dialog আটকে গেলে এই উপসর্গ হবে; রিপোর্টের সেশনে তা ঘটেছিল কি না নিশ্চিত নয়। পৃথক নিশ্চিত ত্রুটি: Action:173–180-এ ID মিলেছে কি না বা save-এর boolean না দেখেই success। শেষ ডিভাইস মুছলেও পরের **read**-এ নতুন default device লিখে ফেলে (Action:37–64)। [সাধারণ metadata read](../lib/sessions.ts#L197-L231) ব্যর্থ হলেও `{}` ফেরাতে পারে; পড়া ব্যর্থ আর সত্যিকারের খালি তালিকা এক নয়।

**ফিক্স:** ব্রাউজারের `confirm`-এর বদলে নাম ও সিরিয়ালসহ অ্যাপের নিজস্ব নিশ্চিতকরণ, বাতিল, pending ও দৃশ্যমান error দিন। ক্লিক → dialog → server result → reload-এ ID অনুপস্থিত—প্রতিটি ধাপ যাচাই করুন। সার্ভারে tenant ও সুনির্দিষ্ট ID মেলান; না পাওয়া বা save ব্যর্থতা success নয়। নিশ্চিত write-এর পরেই তালিকা/টোস্ট বদলাবে। তালিকা পড়লে ডিভাইস তৈরি হবে না। কনফিগ সরলেও পুরোনো পাঞ্চ, হাজিরা ও অডিট থাকবে; সরানো ডিভাইস নতুন পাঞ্চের উৎস হবে না।

### ২. এক-ক্লিকে ম্যাপিং

UI:227–243, 725–734-এ একই `confirm` ও uncaught promise-এর পথ। Action:379–391, 454–466-এ দুই roster query-এর `error` ও metadata save-এর ফল উপেক্ষিত। ফলে ‘কেউ যোগ্য নেই’, ‘সবাই আগে থেকেই ম্যাপড’ ও ‘ডেটা পড়াই যায়নি’ আলাদা হয় না। `students.student_id` সরাসরি select করা হচ্ছে; [বেস টেবিলে](../supabase_schema.sql#L22-L34) এই কলাম নেই, অথচ [শিক্ষার্থীর প্রোফাইল থেকে](../lib/sessions.ts#L295-L329) অফিসিয়াল কোড পাওয়া যায়। তাই এই schema-তে query ব্যর্থ হতে পারে যদিও ম্যানুয়াল তালিকায় শিক্ষার্থী দেখা যায়। কোন deployed schema-তে এটি ঘটেছে, আলাদাভাবে যাচাই দরকার।

আরও একটি পরিচয়গত ভুল: Action:405–445-এ roll/সূচক/ফোনের শেষ চার অঙ্ক থেকে অনুমান, সংঘর্ষে `_…` বা `T…`; শিক্ষক হিসেবে `users.id` নেওয়া হয়। ম্যানুয়াল শিক্ষক ফর্মও `tch_…` বানায় (UI:1465–1480)। কিন্তু [teacher_attendance.teacher_id](../supabase_schema.sql#L161-L169) চায় `teachers.id`।

**ফিক্স:** অনুমোদিত tenant-এর paginated, schema-সমর্থিত roster ও সংরক্ষিত প্রোফাইল ID পড়ুন; শিক্ষককে প্রকৃত `teachers.id` দিয়ে নির্বাচন/যাচাই করুন। নির্ভরযোগ্য machine PIN বা মেশিনে ব্যবহৃত বলে নির্ধারিত unique roll/code-তেই স্বয়ংক্রিয় মিল; দুই শ্রেণিতে এক roll, unlinked staff বা আন্দাজের ID হলে ম্যানুয়াল review। বিদ্যমান manual mapping ও RFID অক্ষুণ্ণ থাকবে। যন্ত্রভেদে একই PIN অন্য ব্যক্তির হলে device scope স্পষ্ট করুন; পুরোনো tenant-ব্যাপী mapping নীরবে প্রথম ডিভাইসে সরাবেন না। UI-তে তৈরি/আগে ছিল/অমিল/দ্ব্যর্থক/ব্যর্থ আলাদা ফল; ০ হলেও কারণ থাকবে। দুবার চালালে দ্বিতীয়বার নতুন mapping ০।

### ৩. একই পাঞ্চ একাধিকবার জমা

Action:600–686 প্রতি লাইনে নতুন log ID দেয়। Action:691–719-এর `Map` শুধু এক batch-এর **ব্যক্তি + দিনের হাজিরা** এক করে; পাঞ্চ লগকে নয়। প্রতিবার `newLogs` সামনে বসিয়ে সম্মিলিত তালিকার প্রথম ৫০০ সারি রাখা হয়; event key পরীক্ষা নেই। [JSON push](../app/api/biometric/push/route.ts#L220-L250) ও [iClock](../app/api/biometric/iclock/cdata/route.ts#L203-L235)-এও আলাদা লেখার পথ। UI-তে দেখা ১৫০টি বা metadata-র ৫০০টি সারি দেখে স্থায়ী ডুপ্লিকেট ঠেকানো যায় না।

**ফিক্স:** আগে §৪–৫ অনুযায়ী সময় ও ID স্বাভাবিক করুন। পাঞ্চের চাবি হবে **`(madrasa_id, device_id, device_user_id, punch_instant)`**; ফাইলের নাম বা import-এর সময় নয়। Action:556–559-এর মতো অচেনা যন্ত্রে প্রথম ডিভাইস ধরে নেবেন না। প্রস্তাব: tenant-সীমাবদ্ধ পাঞ্চ টেবিলে এই চাবির `UNIQUE`, একই ফাইলের জন্য দ্রুত in-memory check, আর পুনরায়/একযোগে আসা ফাইলের চূড়ান্ত সিদ্ধান্ত DB-তে। USB, iClock ও push একই সংরক্ষণপথ ব্যবহার করবে। দুই সময়ে একই ব্যক্তির দুটি পাঞ্চ বৈধ, তার দিনের হাজিরা একটি। সমান চাবিতে পরস্পরবিরোধী তথ্য হলে overwrite নয়, review।

### ৪. বৈধতা পরীক্ষা ও ইমপোর্টের ফল

Parser:102–169-এ header ও ছোট লাইন নীরবে বাদ যায়, ID শুধু non-empty হলেই চলে, সময় না পেলে `08:00:00`, তারিখ বোঝা না গেলে `new Date()`। শুধু regex দিয়ে বছর-মাস-দিন মেলানোয় অসম্ভব ক্যালেন্ডার তারিখও বাদ পড়ে না। Action:610–629-এ manual mapping না থাকলে roll/code-ও খোঁজে; অমিল হলে `unmapped` লেখে। Action:647–752-এ DB সফল হওয়ার **আগেই** `totalProcessed++`; upsert-এর error কেবল console-এ, metadata write ব্যর্থতাও ফলাফলে নেই। স্থানীয় পরীক্ষায় attendance write প্রত্যাখ্যাত করেও `success:true`, `totalProcessed:1` ও `processed` লগ পেয়েছি, যদিও নতুন হাজিরা নেই। UI:1007–1026-এ সারাংশ ও তারিখ, লাইনভিত্তিক কারণ নয়।

**ফিক্স:** ফরম্যাটভিত্তিক কঠোর parser: মূল লাইন নম্বর, তারিখ/সময়ের সীমা, অধিবর্ষ, header/ফাঁকা লাইন স্পষ্টভাবে চিহ্নিত। ZKTeco numeric PIN-এ `ABC` বাতিল; `00012` থাকবে string। প্রকৃত alphanumeric/RFID ব্যবহৃত হলে সেটি কেবল ঘোষিত profile-এ অনুমোদিত। `23/11/2026 08:15` অনুমোদিত ফরম্যাট না হলে কারণসহ reject; আজকের দিন বা কাল্পনিক সময় নয়। বৈধ কিন্তু অচেনা `999999` হারাবে না: **সতর্কতাসহ আনম্যাপড**, কোনো হাজিরা নয়। ভুল audience ও roster পড়তে ব্যর্থ হওয়াকে ‘অজানা ব্যক্তি’ বলবেন না।

রিপোর্টে `ডেটা লাইন = নতুন পাঞ্চ + ডুপ্লিকেট + বাতিল + নীতিমাফিক বাদ` (header/ফাঁকা আলাদা); নতুনের মধ্যে mapped/unmapped, বাতিলের নম্বর ও কারণ, এবং **সত্যি সংরক্ষিত ব্যক্তি-দিন** আলাদা। write ব্যর্থ হলে success নয়। পাঞ্চ ও হাজিরার ফল একই transaction-এ নিশ্চিত করুন, অথবা পাঞ্চকে retry-যোগ্য pending রাখুন; হাজিরা commit ছাড়া `processed` নয়।

### ৫. সময় ছয় ঘণ্টা এগিয়ে যায়

Parser:154–165 স্থানীয় ঘড়ির শেষে `Z` বসিয়ে UTC ঘোষণা করে। UI:1081 `format(new Date(log.punch_time), …)` চালায় ব্রাউজারের timezone-এ। এটি শুধু ঘড়ি দেখানোর ভুল নয়—ভুল instant দিয়ে ডুপ্লিকেট চাবিও বদলাবে। iClock একই parser নেয়; JSON push-এ invalid/missing timestamp-এ আলাদা ‘এখন’ fallback আছে (`push/route.ts:131–138`)।

**ফিক্স:** offset-ছাড়া সমর্থিত মেশিনের সময় `Asia/Dhaka`; offset/`Z`-সহ বৈধ push সময় ইতিমধ্যে একটি instant—দ্বিতীয়বার offset নয়। একবার UTC instant সংরক্ষণ, `punch_date` হবে ঢাকার স্থানীয় দিন; UI ও প্রাথমিক date filter-এও স্পষ্ট ঢাকা zone ([বিদ্যমান date helpers](../lib/date-utils.ts#L16-L34))। যেমন ২৩ নভেম্বর `07:55` → `01:55Z` → পর্দায় `07:55`; `00:05`-এর UTC আগের দিন হলেও হাজিরা **২৩ তারিখেই**। পুরোনো সব timestamp থেকে গণহারে ৬ ঘণ্টা বিয়োগ করা যাবে না।

### ৬. ম্যাপিং করার আগের পাঞ্চ

Action:285–312 ও 454–462 কেবল mapping সংরক্ষণ করে; `biometric_logs`-এর `unmapped` সারির জন্য কোনো replay নেই। নতুন import-ই নতুন mapping পড়ে। এটিই ২২ তারিখের নতুন পাঞ্চ কাজ করা অথচ ২৩ তারিখের পুরোনো পাঞ্চ না বদলানোর ব্যাখ্যা। iClock-এ `if (targetId)` ব্লকের বাইরে কোনো unmapped log-ও লেখা হয় না (`cdata/route.ts:144–201`); না-থাকা ইতিহাস উদ্ধার হয়েছে দাবি করা যাবে না।

**ফিক্স:** mapping save/auto-map শেষে **“পুরোনো পাঞ্চ মিলিয়ে দেখুন”**: tenant, ডিভাইস, PIN ও প্রযোজ্য তারিখসীমায় কেবল unresolved সারির preview। PIN পুনর্বণ্টন, ভুল পুরোনো সময় বা বিদ্যমান হাজিরার ভিন্ন সিদ্ধান্ত হলে আলাদা review। অনুমোদনে একই মূল event-কে নতুন করে append না করে হাজিরা সংযোগ/অবস্থা আপডেট; বিদ্যমান `Present`-এ দ্বিগুণ গণনা নয়, manual `Absent/Late`, `Leave` বা `leave_request_id` নীরবে বদল নয়। একই batch আবার চালালে আর কোনো পরিবর্তন নয়। কাজ করা manual mapping → নতুন পাঞ্চ → হাজিরার পথটি regression test হিসেবে থাকবে।

### ৭. কার্ডে বানানো IP ও অবস্থান

UI:157–170 নতুন ফর্মের **মান** হিসেবেই `192.168.1.201`, `4370`, `প্রধান প্রবেশদ্বার` বসায়—এগুলি placeholder নয়। UI:1192–1291-এ এগুলি সম্পাদনার input নেই; UI:627–640-এ protocol না দেখেই মান থাকলে দেখায়। Action:125–130-এ port-এরও default আছে। অর্থাৎ অন্য কার্ড থেকে IP পড়ছে এমন প্রমাণ নেই; একই default বারবার সংরক্ষিত হচ্ছে।

**ফিক্স:** নতুন ডিভাইসে IP/location খালি। শুধু `lan_tcp`-তে IP ও port ইনপুট, server-side ঠিকানা/port (১–৬৫৫৩৫) যাচাই; Cloud Push/USB-তে LAN fields পাঠানো বা কার্ডে দেখানো নয়। অবস্থান ঐচ্ছিক ও সম্পাদনযোগ্য। পুরোনো ডিভাইসের IP/location কেবল default-এর সমান বলে মুছবেন না।

## বাস্তবায়নের ক্রম ও রিলিজ গেট

1. **প্রথম পরিবর্তন — ব্যবহারকারীর নিয়ন্ত্রণ (#১, #২-এর UI, #৭, #৮-এর feedback)।** নিশ্চিতকরণ, typed action result, save যাচাই, নির্বাচিত ID, read-এ default সৃষ্টি বন্ধ। Desktop ও মোবাইল/embedded browser-এ click/cancel/confirm, permission denial, storage failure, reload এবং শেষ ডিভাইস সরানোর পরীক্ষা। whitespace-only নাম এখনও বাতিল হবে।
2. **দ্বিতীয় — পাঞ্চের মান ও mapping (#৪, #৫, #২-এর roster)।** আগে parser ও identity-র unit tests। নিচের fixture, মধ্যরাত, leap day, invalid time, explicit offset, leading zero, duplicate roll, প্রকৃত teacher FK ও আগের manual mapping পরীক্ষা। Browser timezone বদলালেও একই ঢাকা সময় দেখাতে হবে।
3. **তৃতীয় — স্থায়ী uniqueness ও হিসাব (#৩, #৮-এর কাউন্টার/অডিট)।** [বর্তমান metadata writer](../lib/sessions.ts#L261-L289) পুরো metadata snapshot `registration_no`-তে লেখে; পাশাপাশি দুই save-এ পরিবর্তন হারাতে পারে। অবশিষ্ট device/mapping edit-এ tenant-সীমিত atomic patch/version check; নতুন punch store-এ DB uniqueness ও attendance ফল একসঙ্গে সুরক্ষিত করুন। SQL আগে restored staging-এ, tenant বিচ্ছিন্নতা, অনুমতি/RLS, দুই concurrent import, অন্য ডিভাইসে একই PIN/instant, ৫০০-এর বেশি ইভেন্টের পর পুরোনো ফাইল পুনরায় import ও write failure পরীক্ষা। [মোবাইল device তালিকা/নিবন্ধন](../app/api/mobile/biometric/route.ts) ও [attendance backup/restore](../lib/backup-modules.ts#L156-L159) পুরোনো স্টোরে লিখে যেন পরিবর্তন হারায় না।
4. **শেষ — ইতিহাস মিলানো (#৬) ও নিয়ন্ত্রিত চালু।** আগে backup restore ও প্রতি ডিভাইস/তারিখে লগ বনাম উপস্থিতি গুনে baseline নিন। পুরোনো JSON অক্ষত রেখে raw line ও source থাকলে তবেই timestamp/key মেলান; duplicate-এর মূল log ID-গুলি evidence হিসেবে রাখুন। অস্পষ্ট/হারানো (>৫০০ থেকে বাদ পড়া) তথ্য review-তে, বানানো history নয়। নতুন writer চালুর সময় পুরোনো writer থামান; rollout থামাতে import/replay স্থগিত করে সংরক্ষিত event মিলিয়ে নিন, পুরোনো snapshot দিয়ে নতুন হাজিরা মুছবেন না।

**একটি নির্দিষ্ট গ্রহণযোগ্যতা পরীক্ষা:** ধরা হলো roster সফলভাবে পড়েছে, শুরুতে কোনো PIN-এর নিশ্চিত মিল নেই। সাত লাইন: `480001`-এর একই সকালের পাঞ্চ দুবার ও বিকেলে একবার; `480002` ও `999999`-এর একটি করে; `ABC`-র একটি; `480001`-এর একটি অসমর্থিত `23/11/2026 08:15`। numeric ZKTeco profile-এ প্রত্যাশা:

| পদক্ষেপ | প্রত্যাশিত ফল |
|---|---|
| প্রথম import | ৭ = ৪ নতুন (আনম্যাপড ও সতর্কতা) + ১ ডুপ্লিকেট + ২ বাতিল, হাজিরা ০। |
| একই ফাইল দ্বিতীয় ও তৃতীয়বার | প্রতিবার নতুন ০, ডুপ্লিকেট ৫, বাতিল ২; মোট অনন্য পাঞ্চ ৪-ই। |
| `480001` ম্যাপ করে ২৩ তারিখের preview → অনুমোদিত replay | ঐ PIN-এর ২টি পৃথক পাঞ্চ, ১টি ব্যক্তি-দিন `Present`, অন্য ২টি unresolved। আবার replay-তে ০ পরিবর্তন। |
| ২২ তারিখে নতুন বৈধ mapped পাঞ্চ | আগের মতো নতুন দিনের `Present`; ২৩ তারিখের হাজিরা অপরিবর্তিত। |

**রিপোর্টের ডেটার সীমানা:** ২২টি পুরোনো log মানে ২২টি হাজিরা নয়। রিপোর্টে উল্লিখিত ২২ নভেম্বরের সংরক্ষিত উপস্থিতি ও `480001` manual mapping রাখুন; ২৩ তারিখের ১৮টি একই ব্যক্তির ধরে নেবেন না, ২৫ তারিখের ৩টি raw প্রমাণ ছাড়া অন্য দিনে সরাবেন না। ফিক্স যাচাই ও অপারেটরের অনুমোদনের পরে শুধু সংশ্লিষ্ট tenant + device ID + `TESTSERIAL0001` + `TEST-BIOMETRIC-DELETE-ME` মিললে টেস্ট ডিভাইস সরানোর পরীক্ষা হবে। **আসল মেইন গেট ডিভাইস, পুরোনো পাঞ্চ ও উপস্থিতি মোছা হবে না।**
