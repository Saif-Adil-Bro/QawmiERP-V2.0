# Phase 2: ক্যাশবই, ফান্ড জার্নাল ও ডেবুক

**চালুর ক্রম:** [Phase 1 যাচাই](./finance-integrity-rollout.bn.md) → পুনরুদ্ধার করা staging কপিতে `supabase_finance_integrity_migration.sql`-এর বর্তমান সংস্করণ নিশ্চিত করুন → `supabase_finance_cashbooks_migration.sql` → নতুন অ্যাপ। অ্যাপ বদলানোর আগে মাইগ্রেশন দিন। পুরোনো কর্মী বা পুরোনো রসিদে কোনো নগদ মালিকানা অনুমান করে লেখা হয় না। পুরোনো client বন্ধ না করে নতুন ক্যাশবইকে পূর্ণাঙ্গ ঘোষণা করবেন না।

## অপারেটরের দিন

`হিসাবরক্ষণ → আমার ক্যাশবই` (`/dashboard/accounting/cashbook`) খুলুন। তারিখ বেছে **দিনের শুরুর হাতে গোনা নগদ** একবার লিখুন। এটি ফান্ডের প্রারম্ভিক জমা নয়। একই অ্যাকাউন্ট একাধিক ক্যাশিয়ার ব্যবহার করবেন না।

**প্রত্যাশিত = শুরুর নগদ + নগদ রসিদ − নগদ খরচ + গৃহীত হস্তান্তর − প্রদত্ত হস্তান্তর − ব্যাংকে জমা।** যেমন: শুরু ৳১০, আদায় ৳২৫.২৫, খরচ ৳৫.২৫, হস্তান্তর ৳৮ ও ব্যাংক জমা ৳১০ হলে প্রত্যাশিত ৳১২। হাতে ৳১১.৫০ থাকলে পার্থক্য **−৳০.৫০**; কারণ ছাড়া বন্ধ করা যাবে না।

- `Cash` মানে হাতে থাকা টাকা। **Nagad ওয়ালেট নগদ নয়**; bKash, ব্যাংক, চেক, অনলাইন গেটওয়ে ও অজানা পদ্ধতিও নয়। ফি ছাড়/মওকুফ নয়; এক রসিদে একাধিক বরাদ্দ ও পুরোনো ফি অনুলিপি থাকলেও টাকা একবারই ধরা হয়। মাহফিলের ভেতরের আদায় কেন্দ্রীয় ক্যাশবই নয়।
- হস্তান্তরের জন্য একই তারিখে গ্রহীতার ক্যাশবই খোলা থাকতে হবে। প্রস্তাব পাঠালেই টাকা সরবে না; গ্রহীতা হাতে পেয়ে গ্রহণ করলে দুই ক্যাশবই একসঙ্গে বদলায়। ব্যাংক জমার ক্ষেত্রে স্লিপের রেফারেন্স লিখুন। এগুলোর কোনোটিই প্রতিষ্ঠানের ব্যয় নয়।
- দিন বন্ধের আগে অপেক্ষমাণ হস্তান্তর মেটান। বন্ধ করার পর ওই দিনের নগদ অঙ্ক বদলায় এমন নতুন পোস্ট/বাতিল/পুনর্বহাল প্রত্যাখ্যাত হয়। গণনার পরে হিসাব বদলালে পুনরায় মিলিয়ে নিন। পার্থক্য ঢাকতে দান বা ব্যয় বানাবেন না।

## ফান্ডের জার্নাল

`/dashboard/accounting/journals` থেকে কারণ ও কার্যকর তারিখসহ জার্নাল পোস্ট করুন। স্থানান্তরের **একটি JV নম্বর, একটি অঙ্ক, দুটি ফান্ড**: উৎসে বিয়োগ এবং গন্তব্যে সমান জমা। কোনো দাতা, দান, প্রতিষ্ঠানগত আয়/ব্যয় বা হাতে নগদ তৈরি হয় না। নিষ্ক্রিয়/ভিন প্রতিষ্ঠানের ফান্ড, একই উৎস ও গন্তব্য, লক করা সময়কাল, যাকাত/গোরাবা থেকে স্থানান্তর অথবা বিয়োগ সমন্বয় অনুমোদিত নয়। উৎসের স্থিতি বা মূল বই বদলে গেলে আবার যাচাই করুন।

প্রতি ফান্ডের তারিখযুক্ত প্রারম্ভিক জার্নাল একবারই দেওয়া যায়। **শুধু আগে খাতায় না-আসা জের** দিন; পুরোনো রসিদে ধরা স্থিতি আবার দেবেন না। পরবর্তী অ-দান সংশোধনে জমা/বিয়োগ সমন্বয় ব্যবহার করুন। শুরা বিবরণীর পুরোনো হাতে দেওয়া প্রারম্ভিক স্থিতি পূর্ণ জের হিসাবে ব্যবহৃত হয়; গণনাকৃত জের নিতে ঐচ্ছিক ঘরটি ফাঁকা রাখুন।

## খরচ ও ডেবুক

`/dashboard/accounting/expense-heads`-এ নিজস্ব খাত তৈরি, নাম সংশোধন অথবা নিষ্ক্রিয় করুন। ব্যয়নীতি (যেমন Food) ও পুরোনো ভাউচারের খাতের নাম অপরিবর্তিত থাকে। যাকাতের খাবার খরচে যোগ্য উপকারভোগীর পরিচয় এখনও আবশ্যক।

নতুন খরচে আইটেমভিত্তিক মোডে প্রতিটি পণ্যের নাম ও টাকার অঙ্ক দিন; পয়সা পর্যন্ত যোগফল ভাউচারের সমান হতে হবে। প্রযোজ্য হলে শিক্ষার্থী/কর্মী নির্বাচন করুন। অনুমোদনাধীন আবেদন ব্যয় নয়; চূড়ান্ত পোস্টের পর ভাউচার বা ডেবুকের **মেমো** থেকে সরবরাহকারীর JPG/PNG/WebP ছবি (সর্বোচ্চ ২ মেগাবাইট) যুক্ত করুন। ছবি যাচাই করে metadata ছাড়া JPEG রাখা হয়; এটি public URL নয়। এক ভাউচারে একটি অপরিবর্তনীয় মেমো। ভুল হলে মূল নথি রেখে নিয়ম অনুযায়ী বাতিল ও নতুন ভাউচার করুন।

`/dashboard/accounting/daybook`-এ তারিখ, আয়/ব্যয়/উভয়, ফান্ড, শিক্ষার্থী, কর্মী, রসিদ বা পৃথক আইটেমের নাম ধরে খুঁজুন। প্রিন্ট/PDF-তে নির্বাচিত ফল ও যোগফল যায়। বাতিল ভাউচার চিহ্নিত থাকে, যোগফলে নয়। ঐতিহাসিক বিবরণ থেকে নতুন আইটেম বা কর্মীর পরিচয় আন্দাজ করা হয় না।

## Staging-এ গ্রহণের আগে

1. দুটি পৃথক প্রতিষ্ঠান ও অন্তত দুই ক্যাশিয়ার দিয়ে নগদ/ব্যাংক/ওয়ালেট রসিদ, দুই-পক্ষের হস্তান্তর, ব্যাংক স্লিপ, দিন বন্ধ, এবং বন্ধ দিনের প্রত্যাখ্যান মিলিয়ে দেখুন।
2. একটি JV দিয়ে দুই খতিয়ান, ডেবুক, মাসিক/বার্ষিক/নির্বাহী বিবরণী ও দাতার ইতিহাস মিলিয়ে দেখুন। যাকাত → সাধারণ প্রত্যাখ্যাত হতে হবে।
3. দুই আইটেমের ভাউচার, সীমার বেশি ব্যয়ে দ্বিতীয় স্বাক্ষর, আইটেম ফিল্টার, প্রিন্ট এবং ভিন প্রতিষ্ঠানের মেমো পড়া/লেখা নিষিদ্ধ কি না পরীক্ষা করুন।
4. **Private database backup ছাড়া ছবি পুনরুদ্ধার হবে না।** অ্যাপের JSON export-এ মেমোর সূচি, দৈর্ঘ্য ও SHA-256 থাকে, ছবির bytes নয়। বিচ্ছিন্ন DB restore-এ `treasury_*` টেবিল, ভাউচার ও মেমো মিলিয়ে নিন। Financial/full generic import দিয়ে এসব পুনর্লিখন করবেন না।
5. স্থানীয় regression: `npm test`, `npm run test:e2e`, `npm run test:finance:sql`, `npm run test:finance:browser`, `npm run lint`, `npm run build`। শেষ build ও browser fixture-এর build কম মেমরির মেশিনে একসঙ্গে চালাবেন না। প্রকৃত cut-off, হাতে গণনা, ব্যাংক প্রমাণ ও অনুমোদন staging-এ না মেলা পর্যন্ত production rollout স্থগিত রাখুন।

### দুই প্রতিষ্ঠানের read-only প্রিফ্লাইট

অনুমোদিত **restored staging**-এর `QAWMI_STAGING_DATABASE_URL` secret manager থেকে দিয়ে চালান:

```sh
npm run --silent preflight:cashbooks -- "$TENANT_A" "$TENANT_B"
```

একই read-only snapshot-এ fees, Phase 1 এবং Phase 2 যাচাই হয়। কেবল A/B ও গণনা বেরোয়, নাম/ছবি/রসিদের বিস্তারিত নয়। `0 CHECKS_CLEAR` মানে এই পরীক্ষায় আপত্তি নেই, উৎপাদনে ছাড় নয়। `1 HOLD`-এ অনিষ্পন্ন হস্তান্তর, গণনার গরমিল বা আগের খাতা যাচাই করুন। ব্যাখ্যাসহ সঠিক পার্থক্যও হিসাব বিভাগের স্বাক্ষরের জন্য REVIEW-তে থাকে। কোনো সংরক্ষিত close তার উৎসগুলোর সঙ্গে না মিললে, কোনও posting guard অকার্যকর হলে অথবা ভূমিকার grant ভুল হলে **BLOCK**। `2 INCOMPLETE`-তে মাইগ্রেশনের ক্রম, সংযোগ, অধিকার ও timeout যাচাই করুন—খালি রিপোর্টকে পরিষ্কার ফল ধরবেন না। DBA-র restore পরীক্ষায় একই প্রিফ্লাইট পুনরায় চালান।

### এই শাখায় স্থানীয় যাচাই

| যাচাই | ফল |
|---|---|
| Unit / E2E | ২২১/২২১ এবং ১৪৯/১৪৯ সফল |
| Disposable PostgreSQL | আগের ৭টি যাচাইসহ মোট ১১টি PASS; cash-date, বন্ধ দিনের উৎস, বাতিল হস্তান্তর, সমসাময়িক জার্নাল, migration পুনঃপ্রয়োগ ও আলাদা cold restore অন্তর্ভুক্ত |
| Mounted HTTP / Chromium | ১৬টি PASS; ফিল্টার করা প্রিন্ট, পুরোনো তারিখের BI, web/mobile স্থিতি, দ্বিতীয় স্বাক্ষর ও salary privacy সহ |
| নির্বাচিত অ্যাপ export | ৫০১টি মেমোর সব সূচি; SHA-256 ও byte count মূল ছবির সঙ্গে মেলে। দুই অপারেটরের ৫০০-র বেশি দিন ঠিক একবার করে এসেছে। ছবির bytes বা অন্য প্রতিষ্ঠানের মেমো ফাইলে নেই। আর্থিক import প্রত্যাখ্যাত। |
| অন্যান্য regression | TypeScript, production build (৫২/৫২ static pages), portal parity/preflight, Hifz upgrade ও student health সফল |

**Cut-off / ফেরত যাওয়ার নিয়ম:** চালুর আগে পুরোনো ও নতুন client-এর পোস্ট বন্ধ রেখে verified backup নিন। হাতে গোনা নগদ ও অনুমোদিত ফান্ড জের আলাদা করে লিখিত রাখুন। নতুন ভাউচার পড়ে যাওয়ার পর সমস্যা হলে নতুন পোস্ট বন্ধ করুন; খাতা ফেলে দিয়ে বা শুধু অ্যাপের পুরোনো সংস্করণ চালু করে সমাধান করবেন না। DB ও একই সময়ের অ্যাপের বিচ্ছিন্ন কপি পুনরুদ্ধার করে হিসাব বিভাগকে মাঝের পোস্টগুলো মিলিয়ে নিতে হবে। স্থানীয় PASS বাস্তব প্রতিষ্ঠানের হিসাব, ব্যাংক বিবরণী বা মুদ্রিত কাগজের স্বাক্ষর নয়।
